# Сохранение предсказаний и повторная обработка

Из корня проекта:

```powershell
backend/.venv/Scripts/python.exe backend/scripts/evaluate_corpus.py --provider nitro --execute --out docs/testing/results/fresh.json
backend/.venv/Scripts/python.exe backend/scripts/evaluate_corpus.py --replay docs/testing/results/fresh.records --out docs/testing/results/replayed.json
```

Первая команда платная: передаёт тестовый корпус настроенному провайдеру. Вторая не обращается к сети и не требует ключа. Для локального контроля доступен `--provider rule`.

Рядом с отчётом создаётся новая папка `.records`: `run.json` содержит время, хеши исходников, корпуса и gold; `document-NNN.json` — текст документа, параметры запросов (включая фактический prompt), ответы модели, итоговые факты и диагностику. Заголовки HTTP, API-ключ и окружение не записываются. Папка должна быть новой: старые результаты не перезаписываются. Её содержимое включает исходные тексты, поэтому режим записи предназначен для контролируемых экспериментов.

Каждый полученный ответ сохраняется атомарной заменой файла до разбора. Если позднее разбор или следующий документ упадёт, полученные ответы останутся на диске. Автоматического продолжения незавершённого прогона пока нет.

Replay исполняет обычный модельный разбор, канонизацию и правила восстановления, подставляя ответы только на транспортном уровне. Изменение исходного текста, prompt, модели, параметров запроса или разбиения документа вызывает ошибку несовместимости: такой эксперимент требует нового модельного прогона. Изменения обработки фактов и оценщика можно проверять на тех же ответах. Разные запуски сохраняются отдельно; один replay не измеряет вариативность модели.

Старый отчёт M1 без ответов восстановить в такую запись невозможно. Новые платные вызовы для проверки функции записи не требуются: тест `test_recording.py` проверяет идентичность фактов, отсутствие сети и сохранение ответа при ошибке разбора.
