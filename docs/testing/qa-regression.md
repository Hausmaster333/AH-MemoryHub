# Сквозные проверки QA

Запуск из корня проекта с установленными test-зависимостями:

```powershell
backend/.venv/Scripts/python.exe backend/scripts/evaluate_qa.py --out qa-report.json
```

Скрипт автоматически наполняет отдельную память каждого случая через API ingestion, затем задаёт естественный вопрос через API queries. Парсер rule, ответ local, профиль directed_v1. Вызовы модели запрещены. Работающий сервер и его память не используются.

В `qa-regression.json` — 30 небольших регрессионных случаев: непосредственная причина и следствие, цепочка первопричины, несколько причин, циклы, повторные свидетельства, отрицания причинности и применения инструмента, временные границы состояния, ложные временные дополнения, неизвестные объекты и похожие идентификаторы.

Успех требует ожидаемого ответа, цитат с точными исходными смещениями, необходимых свидетельств, принадлежности целей рабочей памяти и пересчитанного замыкания зависимостей до вопроса. Отказ проверяется вместе с отсутствием цитат и пути ответа. Ответы и результаты наполнения сохраняются по каждому случаю; отчёт содержит хеши корпуса и кода. Ненулевой exit code означает провал проверки.

Это набор, на котором исправлялись ошибки, а не независимая оценка точности, официальный M2 или замена сравнения AH/RAG. Существующий M2 activation fixture остаётся отдельным измерением.

Ограничения: распознавание формулировки вопроса и временных границ остаётся правиловым. Проверка номера устройства не решает произвольную кореференцию; поддержанные отрицания отклоняются, но отдельные отрицательные утверждения пока не хранятся. Сложное предложение с отрицанием и положительной причинностью может быть консервативно отклонено целиком.

## Память из модельных предсказаний

```powershell
backend/.venv/Scripts/python.exe backend/scripts/evaluate_qa.py --corpus docs/testing/qa-recorded.json --records PATH_TO_RECORDS --out model-qa.json
```

`PATH_TO_RECORDS` — каталог завершённого recording/replay с `run.json` и `document-*.json`. Прогон компилирует сохранённые CandidateFacts всех документов в одну память, затем задаёт 35 вопросов из `qa-recorded.json`. Он не извлекает факты повторно и не вызывает модель ответа. Для нового извлечения сначала нужен отдельный replay через evaluate_corpus.py.

Проверяются хеши исходных текстов, совпадение источников с QA-корпусом, ожидаемые фрагменты ответа, цитаты, принадлежность свидетельств нужному документу и трасса активации. Отчёт фиксирует хеш каждого recording, код извлечения из manifest и текущий код движка. Ненулевой exit code допустим для диагностического корпуса с известными незакрытыми случаями; отчёт сохраняется до выхода.

На `qa-verified-m1.records` (10 тестовых документов, сохранённые ответы DeepSeek Nitro) автоматически скомпилирован 181 факт без отказов. До исправления выбора TOOL: 22/35; после: 28/35. По группам: причины 10/10, инструменты 10/10, временные границы 3/10, неизвестные объекты 5/5. Среди 30 вопросов с ответом в источнике проходят 23/30. Это фиксированная диагностическая выборка, а не официальный M2 или общая точность.

Семь временных отказов связаны с отсутствующей идентичностью SUBJECT: сохранены «турбина», «секция», «стрелочному посту», «модуль», «анализатор», «линия», «основной пульт», а вопросы содержат номера конкретных устройств. Наличие номера в другом предложении само по себе не доказывает связь. Следующая работа — сохранять и проверять ссылки на упоминания между частями документа при извлечении; проверку номера в ответах ослаблять нельзя.
